# 资源压测修复与复测 · 2026-11-18

本次针对[修复前压测](PERFORMANCE-AUDIT-2026-11-18.md)确认的瓶颈修改代码，并使用同一机器、同一批临时样例和原始脚本复测。CPU 的 100% 表示一个逻辑核心，内存为进程 physical footprint；磁盘数字是内核记账，不代表 SSD 的物理 NAND 写入。不同运行的系统负载和文件系统缓存有波动，数字用于说明本次场景下的变化。

## 修复内容

- 关闭窗口后，文档库轮询在下一次扫描前检查 Workspace 弱引用并退出，避免后台任务随窗口开关次数累积。
- 搜索结果改用虚拟列表；复用规范化搜索文本和命中索引，关闭弹窗释放文本缓存。保持标题优先、键盘选择及结果摘要行为；不超过 100 条结果时完整测量以保留精确滚动条，更大的结果集只测量可见行。
- 大表格缓存完整测量的行高，随后只布局可见行、预取行、固定表头、跨行单元格和待显示的光标目标。编辑、列宽、图片及主题变化会使缓存失效。
- 长代码的高亮区间查找改用有序范围检索；绘制跳过屏幕外硬行，行号仅构建可见部分。修正 GPUI 显式行顶坐标的绘制层界限，避免大量重叠的屏幕外绘制层。长文本排版缓存约 64 MiB，并保留原生行缓存，避免输入时将未修改行重新冷排版。
- 普通根级文本、列表和任务项中的连续字母数字输入 / 退格只更新对应条目，不再遍历全篇重建渲染索引。其他操作走完整重建；开发驱动可将缓存与完整结果比较。
- 已完成冲突检查后，跳过内容相同的 XML 保存，同时保留原修改时间、索引和历史。Markdown 原有的格式保留逻辑继续有效。
- 本机解析缓存改为逐文档增量，累计 64 个文件或出现删除后合并完整快照。generation 隔离旧增量，即使清理中断也不会覆盖新快照。共享 JSON 清单备份优先使用文件系统复制，在 APFS 上实测为写时复制；备份拥有独立 inode，外部原地编辑不会破坏它，失败时退回原子写旧字节。

以上只改变本机缓存格式，没有修改文档库 FORMAT 或笔记格式，也没有操作真实文档库。

窗口场景的原主窗口空闲 CPU 本次为 1.05%，修复前为 10.50%；这两次运行的绝对 CPU 水平不同。关键是关闭次数从 20 增到 40 后没有继续累加，任务也在源码中具有无条件的存活检查。大代码输入仍有约 17.94ms 的命令处理 P95，不能只看 frame 数字。

## 尚存的规模限制

这次消除了已确认的任务泄漏、不可见搜索行开销和多余写入，并没有保证任意文档都能在 16ms 内处理。20 万字符单段修改仍需要原生文本系统重新排版整段，输入帧 P95 为 33.97ms（修复前 36.58ms）；万行代码输入仍有整块语法高亮与排版索引成本。万篇库的共享 `quiet.json` 为现有文档库格式，每次真实元数据变化仍原子写入整份清单；本次减少了解析缓存和备份的额外全量写入。窗口存活时仍按现有周期扫描库目录。补充运行中万篇库主页滚动 P95 为 41.36ms；8 次不命中查询的帧 P95 / 最大值为 107.67ms，仍有首次查询和大库整体界面的成本。

短时间压力测试只能证明这些场景下的资源行为，不能据此宣称应用在所有输入和长期运行下没有内存泄漏。图片缓存及撤销历史的释放仍需结合持续使用观察。
