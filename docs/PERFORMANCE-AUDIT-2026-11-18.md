# 资源与压力测试 · 2026-11-18

确认存在性能、内存占用和写入放大问题。最需要处理的是长代码 / 大表格的整块布局、大量搜索命中的渲染与内存保留，以及窗口关闭后仍运行的文档库轮询。图片解码缓存和大文档撤销历史在离开文档后能够回收，本次没有观察到它们持续增长。

以下记录修复前的基线，保留原始问题和测量口径；对应改动与复测见[修复报告](PERFORMANCE-FIXES-2026-11-18.md)。

## 环境和口径

- Apple M1 Pro，10 核，16 GB；macOS 27.2.1。
- Quiet.md 0.3.6，基础提交 `553fdb2`，release + devtools，1280 × 800 pt，Craft 浅色。
- 全部使用生成的数据和独立临时文档库；正文、本机状态、解析缓存及日志均隔离。没有访问真实笔记，没有使用系统剪贴板、激活窗口或远程服务。
- 14 类场景，另做 6 次专项对照；每个进程顺序运行。记录约 100ms 一次的 `proc_pid_rusage`，并观察文件替换和内容哈希。
- CPU 100% 表示一个逻辑核心。CPU 的 Mach ticks 使用 `mach_timebase_info` 换算，内存以物理 footprint 为主，MiB = 2²⁰ 字节。峰值若有内核记录则采用进程存活期峰值，详见原始数据。
- 窗口在屏幕外运行，应用内编辑焦点和光标闪烁正常；devtools 禁用了 App Nap。空闲使用原生事件循环，不主动请求帧。这不是最小化 / App Nap 状态的测量。
- `bench` 的 frame 只统计同步绘帧，step 单独计命令处理；二者的分位数不能直接相加，也不是端到端输入延迟。文件系统缓存没有清空，启动时间不是冷盘读取时间。
- 逻辑写入和内核记账的磁盘写入分别记录，后者不等于 SSD 的 NAND 写入量。异步保存可能记入下一阶段；资源测量阶段没有截图。

## 已确认的问题

### P1：长代码和大表格会阻塞界面

| 场景 | 实测 |
|---|---|
| 10,000 行 Rust 代码，约 64 万字符 | 到首个测试阶段耗时 **61.57 秒**（含约 4 秒脚本等待），启动阶段 CPU **96.79%**；随后 100 次滚动在进程总计 **180 秒**内未完成，被超时保护结束 |
| 1,000 行 × 8 列表格，100 次滚动 | 帧 P50 **198.87ms**，P95 **204.06ms**，最大 **226.43ms**；CPU **97.53%**，内存峰值约 **502 MiB** |
| 同一大表格，只空闲 20 秒 | 正常闪烁 **42.20% CPU**；关闭闪烁对照 **1.11% CPU** |

代码块的采样热点包括 `editor::text::build_runs` 和 GPUI `BoundsTree::insert/find_max_ordering`。`build_runs` 为每个切分区间线性查找全部高亮 span（[text.rs](../src/editor/text.rs)）；代码行号和文本也整块构建（[render.rs](../src/editor/render.rs)）。表格为全部 8,000 个单元格创建布局（[table.rs](../src/editor/table.rs)），外层文档列表的虚拟化不能省掉表格内部的工作。

光标每 500ms 对 Editor `notify`（[view.rs](../src/editor/view.rs)），在大表格上两次昂贵重绘就足以消耗接近半个核心。关闭闪烁是定位用的对照，不是建议取消产品行为。

建议先减少不可见代码行 / 表格行参与布局和绘制的数量，消除高亮 span 的重复线性查找，并让光标闪烁复用正文布局。

### P1：大量搜索命中造成秒级停顿和约 1 GiB 内存保留

10,000 篇、每篇约 2,000 字符的文档库，搜索 `Note` 命中全部标题：

- 搜索前约 **138 MiB**，进程物理内存峰值 **1,125 MiB**。
- 输入查询并等待的阶段实际耗时 **6.59 秒**，其中脚本主动等待 1.5 秒，CPU **77.32%**。
- 展示结果空闲 10 秒后约 **1,033 MiB**；关闭搜索，再空闲 **35 秒**后仍约 **1,047 MiB**。
- 另一次从主页搜索并打开精确标题的运行也出现约 **1.2 GiB** 的高占用。

不命中的查询也有规模问题：同样 8 次查询，千篇库 frame P95 **15.68ms**，万篇库 **97.80ms**（样本仅 8 次，P95 在这里也是最大值）。

[search.rs](../src/search.rs) 每次查询将全文转小写扫描，渲染时克隆全部结果，再为每一项调用 `search_row`，没有可见行虚拟化。大量不可见结果也创建、测量文字和元素。建议优先虚拟化结果行，缓存搜索规范化文本和查询结果。内存保留的分配级来源尚未完全归因；本次证明了高峰值和关闭后的保留，不能据此断言内存会无限增长。

### P1：关闭窗口后，文档库轮询任务仍存活

同一万篇库、始终只保留原主窗口，额外窗口均不显示、不聚焦，创建后立即关闭：

| 阶段 | 空闲 CPU | 阶段结束内存 |
|---|---:|---:|
| 原始主窗口 | **10.50%** | 131 MiB |
| 累计关闭 20 个窗口 | **27.40%** | 156 MiB |
| 累计关闭 40 个窗口 | **42.77%** | 145 MiB |

每阶段测量 15–20 秒。内存能下降，CPU 随关闭次数累加。

[app.rs](../src/app.rs) 的文档库监测是 detached task：每 2 秒扫描一次；`now == last` 时直接 `continue`，只有形状变化时才通过 `this.update` 发现 Workspace 已销毁并退出。库没有变化时，已关闭窗口的任务会一直扫描。这与增量 CPU 的实测一致。

建议保存 Task 并随 Workspace 释放，或在扫描前无条件检查弱引用是否仍有效，不能把生命周期检查放在“发生文件变化”的分支后面。

### P2：自动保存会重写全库缓存和元数据

万篇库连续输入 **60 个 ASCII 字符**，测量 **17.52 秒**：

| 项目 | 观测结果 |
|---|---:|
| 进程逻辑写入 | **223.63 MiB** |
| 内核记账的磁盘写入 | **220.80 MiB** |
| 正文保存 | 7 次，每次仅约 2.4 KiB |
| 本机解析缓存 | **7 次整文件替换，每份约 24.96 MiB** |
| `quiet.json` | 每份约 **3.38 MiB**，保存同时替换 `.bak` |

写入次数不是逐键保存：2 秒连续输入保存上限在工作。问题是每次保存的范围过大：

1. 正文保存更新共享清单及备份（[virtual_store.rs](../crates/core/src/virtual_store.rs)）。
2. 清单 mtime 变化触发窗口重新 `list()`。
3. 重新解析变更正文后，`save_parsed()` 克隆并序列化全库缓存，再原子写盘（[store.rs](../crates/core/src/store.rs)）。

500 万字的 200 次输入、200 次退格两个阶段也产生约 **349 MiB** 逻辑写入。版本快照有节流，本次大量写入的主要来源不是历史文件数量失控。

建议缓存按文档增量持久化或合并延迟写入，元数据与本机缓存避免在每次正文保存后全库重建；同时把重工作移出界面线程。

### P2：正文无变化也会重新写入 XML

小文档先输入 `x` 再退格，均在自动保存之前完成，重复 8 次：

- 观测到 **8 次正文原子替换，8 次 SHA-256 均与原正文相同**。
- 9.21 秒产生 **2.52 MiB** 逻辑写入、**116 KiB** 内核磁盘写入，包含元数据和缓存的连带写入。
- 对照：干净文档按 50 次 Cmd+S，稳定后写入 **0 字节**；保存完成后的两段各 15 秒原生空闲也都是 **0 字节**。

`Store::write_doc` 的 `same` 优化只用于 Markdown，XML 会无条件写盘（[store.rs](../crates/core/src/store.rs)）。建议在已经完成冲突检查后，同样跳过字节相同的 XML 正文，并避免带动无意义的修改时间、共享清单和解析缓存写入。

### P2：长文档与超长单段仍有输入瓶颈

| 文档 | 输入 frame P50 / P95 | 退格 P95 | 滚动 P95 |
|---|---:|---:|---:|
| 1,001,307 字符混合文档 | **8.62 / 9.82ms** | 10.99ms | 6.29ms |
| 5,006,535 字符混合文档 | **40.21 / 47.32ms** | 43.54ms | 6.48ms |
| 约 122 万字符 Markdown | **3.46 / 4.07ms** | 3.84ms | 6.18ms |
| 200,000 字符单段 | **35.06 / 36.58ms** | 36.78ms | 5.15ms |

每格来自 200 次操作。百万字符在本机大致满足 60Hz 的帧预算，五百万字符和长单段有明显输入延迟。五百万字符输入阶段 CPU **84.19%**、内存峰值约 **796 MiB**。其编辑器 render 占输入帧的大部分；长单段的 editor render 很短，主要成本在后续文本布局。

万篇库真实主页的 120 次滚动 P95 **49.25ms**；源脚本中早期名为 `home-scroll` 的主压测阶段实际仍在文档页，主页结果采用后续显式点击 Home 的专项运行。

## 内存回收与正常表现

- **图片**：24 张 4032 × 3024 图片的库中，三轮各打开 11 篇图片文档再切回纯文字。每轮峰值约 **230–251 MiB**，等待 35 秒后回到约 **83–98 MiB**。另测图片主页滚动，离开后回到约 **95 MiB**。
- **撤销**：百万字符文档 550 次换段、撤销、重做，峰值约 **588 MiB**。主页仍保留最后的 Editor 和撤销历史，留在主页时约 499 MiB 是保留行为；专项测试真正切到另一篇小文档后，从约 **507 MiB** 降到 **97 MiB**，再等待降到 **87 MiB**。
- **文档切换**：两轮各切换 160 篇，空闲末尾约 **115 / 117 MiB**，未观察到按访问篇数持续累积完整正文。
- **小文档空闲**：稳定后约 **70 MiB**，CPU **1.3–1.5%**，没有周期性正文 / 清单 / 缓存写入。
- 撤销的 256 MiB 是估算预算，且至少保留 20 步，不是进程内存的硬上限。本次高占用能回收，不应与搜索结果保留或窗口任务泄漏混为一谈。
